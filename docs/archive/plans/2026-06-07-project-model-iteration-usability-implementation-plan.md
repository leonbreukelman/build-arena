# Implementation Plan — Project Model v1 Iteration Usability Enrichment

Date: 2026-06-07
Spec: `docs/specs/2026-06-07-project-model-iteration-usability-enrichment.md`
Review source: `docs/verification/2026-06-06-fmc-mcp-first-decomposition/three-model-project-model-usability-review.md`

## Objective

Make the Project Model v1 generated by the decomposer useful as an iteration guide, not just a static map. The implementation must enrich the v1 artifact and snapshot output enough that Grok, Opus, and Hermes agree the FMC-MCP review gaps are addressed or explicitly represented.

## Guardrails

1. Do not modify `scorer/`, `verifier/`, root `schema/`, `.arena/scorer.lock.toml`, or `arena/generated/`.
2. Do not mutate FMC-MCP source in this slice.
3. Do not use live FMC credentials or `--allow-live`.
4. Keep v0 output and existing v1 fields compatible.
5. Ground all records in filesystem/git/source evidence from the target repo.

## Phase 1 — Opus-reviewed design

1. Write spec and plan artifacts.
2. Send both to Opus with this review question:
   - Does the spec/plan address every Grok/Opus/Hermes review gap?
   - Is the contract implementable without overfitting to FMC-MCP?
   - Are any acceptance criteria missing before implementation?
3. Patch the spec/plan if Opus identifies valid gaps.
4. Record the Opus review and accepted changes under `docs/verification/2026-06-07-project-model-iteration-usability/`.

Exit criteria:

- Spec and plan exist.
- Opus review exists.
- Accepted feedback is incorporated or explicitly rejected with rationale.

## Phase 2 — Red tests

Add failing tests before implementation:

1. `tests/test_project_graph.py` or existing decomposer tests:
   - repo with `from pkg import resources, tools` produces import edges/contract coverage for both `pkg.resources` and `pkg.tools` when those modules exist.
2. `tests/test_project_decomposer_ai.py`:
   - fixture repo with `client.py`, `server.py`, `resources.py`, and `tools.py` emits non-tautological component responsibilities.
   - client profile/risk signals rank the stateful/auth/rate-limited client ahead of a tiny entrypoint.
   - configured `ruff` and `mypy` commands are detected when present in `pyproject.toml`.
3. `tests/test_project_model_v1_contract.py`:
   - generated v1 has emitted `iterationReadiness` sections.
   - schema validates artifacts with and without the optional field so historical v1 artifacts remain reproducible.
   - v0 compatibility artifact still exists.
   - component responsibility tests reject tautological summaries and require at least two source-derived symbols/tags.

Exit criteria:

- The new tests fail for the expected missing behavior before implementation.

## Phase 3 — Implementation

1. Fix Python import resolution:
   - update `_resolve_python_import` to emit alias-qualified absolute imports for `from pkg import a, b` while still allowing module-level imports like `from pkg.config import VALUE` to resolve to `pkg.config` through existing target-matching logic.
2. Add deterministic source-analysis helpers:
   - map component ids to graph nodes, paths, source text, symbol names, and provenance refs;
   - count lines/classes/functions;
   - derive behavioral tags from source patterns;
   - discover configured local quality commands from `pyproject.toml` and package config.
   - produce source-span-backed inferred records without pretending they are graph call edges.
3. Enrich fixture model output:
   - replace tautological responsibilities with summaries based on detected tags/symbols;
   - add product cross-cutting concerns when deterministic evidence exists;
   - add observable checks for pytest, ruff, and mypy/pyright when configured and safe.
4. Extend `project_model_v1_from_snapshot`:
   - build `iterationReadiness` from snapshot + graph;
   - include component profiles, runtime contracts, external surfaces, product invariants, quality gates, priority backlog, and open questions.
5. Update JSON schema:
   - define optional `iterationReadiness` and validate its nested record shapes while preserving validation for legacy v1 artifacts without the field.
6. Keep all changes deterministic and provenance-backed.
7. Include Opus-flagged non-blocking review signals where source-supported:
   - capture the `FMCClient.test_connection` naming smell as a backlog/open-question item;
   - capture the server-to-tools indirection as a delegation contract plus a question about intentionality.

Exit criteria:

- New red tests pass.
- Existing tests pass.

## Phase 4 — Local verification

Run:

1. `uv run pytest tests -q`
2. `uv run ruff check .`
3. `uv run pyright`

If any fail:

- diagnose root cause;
- patch the implementation or tests;
- rerun the failing check and then the full suite.

## Phase 5 — Regenerate FMC-MCP model

1. Generate a new durable FMC-MCP snapshot under:
   - `docs/verification/2026-06-07-project-model-iteration-usability/fmc-mcp-updated-model/`
2. Command:
   - `uv run python -m arena.project_model_cli snapshot --project /home/leonb/projects/fmc-mcp --artifacts-root <dir> --project-id fmc-mcp --goal "decompose FMC-MCP into iteration-ready responsibility-bearing components" --llm-mode fixture --overwrite`
3. Gate it:
   - `uv run python -m arena.project_model_cli gate --snapshot <manifest.json>`
4. Run target local checks actually exposed as acceptance checks, at minimum:
   - `uv run python -m pytest -q` in FMC-MCP;
   - `uv run ruff check .` if exposed as configured quality gate;
   - `uv run mypy src/fmc_mcp` if exposed as configured quality gate.
5. Write a short regeneration report with snapshot id, gate status, and check outputs.

Exit criteria:

- Updated Project Model v1 exists.
- Gate passes.
- Actual local command output is captured.

## Phase 6 — Three-model agreement

1. Prepare a compact review packet containing:
   - original three-model review;
   - spec and plan;
   - updated Project Model v1;
   - regeneration report;
   - local verification outputs.
2. Ask Grok:
   - Are the original review gaps addressed or explicitly represented?
   - If not, identify blockers only.
3. Ask Opus the same question.
4. Perform the same Hermes grounded review by reading the updated model and source.
5. If any reviewer identifies a valid blocker:
   - implement a bounded repair;
   - rerun local verification;
   - regenerate the model if required;
   - rerun the agreement check for the blocking area.

Exit criteria:

- Grok, Opus, and Hermes all return `agree` or equivalent non-blocking verdict.
- Any non-blocking suggestions are recorded as future work, not hidden.
